## 3. 开始任何开发前必须先做的事

1. 确认用户这次要改的是哪个页面、哪个功能、哪个素材路径。
2. 先用 `rg` 搜索相关节点、脚本、配置、资源名。

4. 判断页面是编辑器节点驱动，还是运行时脚本创建节点。

## 4. 文件结构规则

### 4.1 代码目录

主要代码目录：

```txt
assets/Script
```

建议分工：

| 目录 | 放什么 |
| --- | --- |
| `assets/Script/UI/Home` | 首页、弹窗、功能页 UI 逻辑 |
| `assets/Script/Services` | 登录、运行配置、后端适配、本地服务 |
| `assets/Script/Services/Backend` | 后端接口、DTO、本地/远程 backend |
| `assets/Script` 其他目录 | 按现有工程结构处理，不随便新建大杂烩目录 |

### 4.2 Home 配置文件

`HomeConfig.ts` 已经拆分过，不要再把所有配置塞回一个巨型文件。

当前规则：

| 类型 | 建议文件 |
| --- | --- |
| 道友、头像、资料页 | `HomeProfileConfig.ts` |
| 分享任务 | `HomeShareConfig.ts` |
| 魔界、战斗入口 | `HomeMagicConfig.ts`、`HomeBattleConfig.ts` |
| 商店、购买、确认弹窗 | `HomeShopConfig.ts` |
| 背包、角色装备 | `HomeRoleBagConfig.ts` |
| 通用 UI 资源 | `HomeCommonUiConfig.ts` |

如果以后配置继续变大，继续按功能拆，不要堆到一个文件。

### 4.3 资源和 `.meta`

Cocos 资源必须保留 `.meta`。

不要随便删除或重建这些文件：

```txt
*.meta
assets/**/*.meta
```

不要直接改：

```txt
library
temp
```

这些目录是 Cocos 生成物，通常不是人工维护目标。

## 5. UI 开发规则

### 5.1 用户需要经常调的位置，优先让编辑器可改

如果一个位置、大小、间距以后用户会在 Cocos 编辑器里调，优先做成清晰节点结构：

```txt
RowRoot
├── Bg
├── Avatar
├── NameLabel
├── LevelLabel
├── CurrencyIcon
└── CurrencyLabel
```

不要把一个信息框拆成很多散落节点，否则用户在编辑器里选中和移动会很痛苦。

### 5.2 动态列表必须有统一行节点

道友、分享任务、邮件、商品、背包列表等都按这个结构：

```txt
ScrollView
└── Content
    ├── RowTemplate
    ├── Row_01
    ├── Row_02
    └── Row_03
```

规则：

| 项 | 要求 |
| --- | --- |
| 每一行 | 必须是一个完整根节点 |
| 行背景 | 放在行节点下面 |
| 头像/文字/图标/按钮 | 都是行节点子节点 |
| 模板节点 | 可以隐藏，用脚本克隆 |
| Content 高度 | 根据行数和间距计算 |
| ScrollView 可视高度 | 单独可调，不要和 Content 高度混淆 |

### 5.3 避免脚本覆盖编辑器

如果出现“编辑器里改了，启动后没变化”，通常是脚本运行时做了这些事：

```ts
node.setPosition(...)
uiTransform.setContentSize(...)
node.scale = ...
node.removeAllChildren()
```

处理规则：

1. 先查是哪段脚本覆盖。
2. 如果这个位置以后要常调，把数值移动到配置文件。
3. 如果用户明确想在编辑器调，就不要每次启动强制覆盖。
4. 不要只在编辑器里硬拖，因为下次启动还会被脚本改回去。

### 5.4 资源适配规则

图片底框、按钮、背景这些素材优先使用已有资源和已有封装。

常见要求：

| 类型 | 规则 |
| --- | --- |
| 按钮 | 使用项目已有按钮底框、按钮文字居中 |
| 弹窗 | 使用项目已有弹窗底图、小标题底图 |
| 列表行 | 背景、头像、文本、图标统一在一行节点内 |
| 滚动区域 | 明确区分可视窗口和 Content |
| 数字文本 | 后续可能由后端返回，不能写死在散落 UI 逻辑里 |

## 6. 数据和后端预留规则

### 6.1 继续前端开发不会影响后端

可以继续做前端界面，但每个功能都要按下面方式写：

```txt
本地假数据先跑通
-> 定义清楚数据结构
-> UI 只消费数据，不直接拥有核心规则
-> 后续把数据源替换成后端接口
```

### 6.2 新功能必须先想清楚数据结构

例如道友页不能只写死 UI，至少要有类似结构：

```ts
interface CompanionDto {
    id: string;
    name: string;
    avatarId: string;
    battleLevel: number;
    yuanbao: number;
    type: 'chief' | 'generation';
}
```

分享任务也一样：

```ts
interface ShareTaskDto {
    id: string;
    allyType: 'chief' | 'generation';
    requiredCount: number;
    requiredBattleLevel: number;
    rewardYuanbao: number;
    progress: number;
    claimed: boolean;
}
```

这些类型不一定马上接后端，但要让后端未来能照着返回。

### 6.3 核心数据以后必须服务端为准

下面这些数据前端当前可以本地模拟，但正式上线必须以后端为准：

| 数据 | 原因 |
| --- | --- |
| 元宝、灵石、积分 | 涉及充值、奖励、经济系统 |
| 背包物品数量 | 涉及消耗和奖励 |
| 战斗胜负、奖励 | 涉及作弊风险 |
| 邮件领取状态 | 防止重复领取 |
| 商店购买记录 | 防止刷资源 |
| 分享任务进度 | 防止伪造任务完成 |
| 道友数量和等级 | 涉及邀请、关系链、奖励 |

### 6.4 接口变化要同步文档

如果新增或调整后端接口，要同步更新：

```txt
docs/15_现有接口文档草案.md
```

如果只是前端本地假数据，至少在功能说明里标明“后续需要接后端”。

## 7. 前后端协作规则

前端仓库和后端仓库建议分开：

```txt
前端：duxiachuan-qv1.3
后端：duxiachuan-server
```

前端只负责：

| 前端职责 | 说明 |
| --- | --- |
| UI 展示 | 页面、弹窗、按钮、列表、动画 |
| 本地预览 | 后端没好前也能点、能看 |
| DTO 定义 | 和后端约好字段 |
| 接口调用 | 通过 `IGameBackend` / `RemoteGameBackend` |

后端负责：

| 后端职责 | 说明 |
| --- | --- |
| 登录鉴权 | token、账号、玩家身份 |
| 数据存储 | 玩家、背包、邮件、任务、战斗 |
| 经济校验 | 货币、购买、消耗、奖励 |
| 战斗结算 | 至少做基础校验 |
| 多人数据 | 排行、集市、道友、分享关系 |

不要让 UI 脚本直接拼一堆 `fetch`。统一走后端适配层。

## 8. 新功能标准流程

每做一个新功能，按这个顺序：

```txt
1. 看用户截图和素材路径
2. 定位现有页面、节点、脚本、资源
3. 判断是改编辑器节点还是改运行时脚本
4. 定义本地展示数据和未来 DTO
5. 搭 UI 结构，保证编辑器可维护
6. 接本地假数据跑通
7. 预留后端接口入口或 TODO
8. 运行检查脚本
9. 告诉用户改了哪些文件、在哪里调
```

不要一上来大规模重构。先让这个功能完整可用，再做必要整理。

## 12. 常见问题处理

### 12.1 编辑器改了，启动后没更新

优先检查：

1. 是不是改错工程。
2. 是不是改了归档工程，而不是 `game\Qv1.3`。
3. 是不是运行时脚本重新创建了节点。
4. 是不是脚本里 `setPosition` / `setContentSize` 覆盖了编辑器值。
5. 是不是 Cocos 预览缓存，需要重新启动预览。

### 12.2 列表行拖动不方便

通常是每个信息框不是一个统一根节点。

正确做法：

```txt
一个信息框 = 一个 RowRoot
所有子元素都在 RowRoot 下面
移动 RowRoot 就能移动整行
```

### 12.3 调宽后图片显示不完整

常见原因：

| 原因 | 解决 |
| --- | --- |
| Sprite 九宫格没设好 | 检查 Sprite 的 Type / Trim / Size Mode |
| 父节点裁剪 | 检查 Mask、ScrollView view |
| 脚本强制尺寸 | 查 `setContentSize` |
| 资源本身边缘不足 | 换九宫格素材或调整 inset |

### 12.4 滑动区域高度不对

区分这两个节点：

| 节点 | 作用 |
| --- | --- |
| ScrollView/View | 可见窗口高度 |
| Content | 可滚动内容总高度 |

用户问“滑动上下高度”，通常改的是 ScrollView 或 View 的高度，不是单行节点高度。

## 13. 当前最重要原则

后续开发以这三个目标为准：

```txt
1. 用户能在编辑器里更快调 UI
2. 前端页面先完整跑通
3. 后端以后能按 DTO 和接口顺利接入
```

也就是说，不追求现在就做成最终服务端架构，但不能再写成以后完全无法接后端、无法维护、无法编辑器调整的样子。
