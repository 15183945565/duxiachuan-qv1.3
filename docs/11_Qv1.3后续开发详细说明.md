Qv1.3 已经从“所有页面、资源和逻辑集中在一个大场景与继承链中”的原型工程，整理为更接近正式游戏项目的开发基线。后续开发的目标不是继续堆页面，而是在现有边界内补齐真实 UI、真实数据、后端事务、异常状态、性能和发布能力。

## 3. 每日开发标准流程

### 3.1 开始开发前

1. 确认打开的是 `C:\Users\34158\Desktop\game\Qv1.3`。
2. 使用 Cocos Creator `3.8.8`，不要让其他 Creator 版本自动升级资源。
3. 等待资源导入完成，控制台没有持续报错后再开始修改。
4. 建立版本库基线或创建本次修改分支，先记录当前可运行状态。
5. 明确本次任务属于哪个页面、Prefab、Feature、Bundle 和后端事务。
6. 若修改现有 UI，先记录原节点路径、尺寸、锚点、Widget、SpriteFrame 和脚本引用。

### 3.2 开发过程中

- 固定页面和弹窗在对应 Prefab 中编辑，不在 MainScene 中复制一份。
- 数量不确定的列表行、伤害数字、掉落格子和角色实例由模板或运行时代码生成。
- 同一任务只改有明确归属的文件，避免顺手重命名大量节点或资源。
- 新资源先确定共享/功能归属，再导入；不要先扔进 `res`，之后再讨论拆分。
- 新异步流程必须有重复点击保护、失败恢复和对象销毁后的有效性判断。
- 新事件、Tween、schedule、Spine 回调和 ResourceScope 必须设计对应的解绑/停止/释放时机。
- 页面业务逻辑只依赖 `GameBackend.api`，禁止在 Feature 中直接写 `fetch`。

### 3.3 完成开发后

1. 保存 Scene/Prefab，等待 Creator 导入结束。
2. 检查 Creator 控制台无 Missing Script、Missing Asset 和持续错误。
3. 执行对应专项检查，再执行：

```powershell
npm run check:all
```

4. 从 LoadingScene 跑完整入口，不只从目标页面单独预览。
5. 验证打开、关闭、快速重复点击、返回、重新进入和异常分支。
6. 涉及资源时检查首次进入前后 Bundle 请求和内存变化。
7. 涉及后端时测试成功、业务失败、401、409、超时、断网和重试。
8. 涉及屏幕边缘时至少检查设计比例、20:9 长屏和带安全区设备。
9. 更新相关文档、测试记录、资源版本和接口契约。

## 5. 场景与 UI 层级

### 5.1 场景职责

`LoadingScene` 负责：

- 启动配置和共享资源加载。
- 修复入口。
- 手机号登录。
- 进入 MainScene 前的加载表现。

`MainScene` 只负责：

- 摄像机和 `MainRoot`。
- 游戏场景层。
- 常驻 HUD、左右 Dock 和底部导航。
- Page、Popup、Guide、Toast 六层壳。
- `MainHomeView` 生命周期与按需 Prefab 编排。

禁止为减少加载代码而把功能 Prefab重新拖回 MainScene。这样会重新产生大场景冲突、启动资源泄漏和多人协作覆盖问题。

### 5.2 MainRoot 固定顺序

```text
Canvas
  MainRoot
    GameSceneLayer
    HudLayer
      TopHud
      LeftDock
      RightDock
      BottomNav
    PageLayer
    PopupLayer
    GuideLayer
    ToastLayer
```

同级顺序影响绘制和触摸命中，必须保持：

1. `GameSceneLayer`
2. `HudLayer`
3. `PageLayer`
4. `PopupLayer`
5. `GuideLayer`
6. `ToastLayer`

不要按照“用户先点哪个按钮”排列节点。节点树按渲染层、容器归属和生命周期组织。

### 5.3 Page 与 Popup 的选择

使用 `PageLayer`：

- 占据主要游戏区域或全屏的功能页面。
- 打开后需要隐藏/覆盖主界面主要操作的页面。
- 例如角色、背包、征战、商城、魔界地图。

使用 `PopupLayer`：

- 确认、奖励、详情、列表弹窗和临时遮罩。
- 需要阻挡下层点击时，根节点必须有启用的 `cc.BlockInputEvents`。
- 例如邮件、公告、排行、集市、物品详情、确认弹窗。

使用 `GuideLayer`：

- 新手引导遮罩、手指动画和焦点高亮。

使用 `ToastLayer`：

- 不应被其他页面盖住的轻提示。

## 6. Prefab 开发规范

### 6.1 静态结构与动态内容

应该写入 Prefab：

- 页面根节点、背景、标题、固定按钮和固定页签。
- ScrollView、Viewport、Content 和可编辑模板。
- 固定遮罩、固定布局容器和输入阻挡组件。
- 美术需要在编辑器中持续调整的位置、锚点和尺寸。

允许运行时生成：

- 数量由服务端决定的列表行。
- 背包格子、邮件行、排行榜行和市场商品。
- 战斗演员、怪物、伤害数字、掉落格子和特效实例。

不允许运行时补建：

- `HudLayer/PageLayer/PopupLayer/GuideLayer/ToastLayer`。
- 已约定存在的页面和弹窗根节点。
- 为逃避 Prefab 编辑而创建的同名替代根节点。

### 6.2 修改现有 UI 的流程

1. 在 `HomeUIPrefabManifest.ts` 中确认根节点对应的 Prefab 路径。
2. 在资源管理器中双击目标 Prefab，进入 Prefab 编辑模式。
3. 修改节点的 Position、UITransform、Anchor、Widget、Sprite、Label 或 Layout。
4. 贴边控件优先使用 Widget，不使用只适合单一设备的绝对坐标。
5. 可拉伸底框使用九宫格，不直接拉伸装饰边角。
6. 保持代码依赖的节点名；确需改名时同步修改路径、检查脚本和文档。
7. 保存后运行 `npm run check:ui`。
8. 从真实入口首次打开页面，验证按需加载、遮罩、关闭和再次进入。

### 6.3 新增 Page/Popup 的流程

1. 在 `assets/Bundle/UIHome/Prefabs/Page` 或 `Popup` 新建 Prefab。
2. 根节点使用唯一的 `PascalCase` 名称。
3. 设置正确的 `750×1624` 设计基准、锚点和 Widget。
4. Popup 若阻挡下层交互，添加 `cc.BlockInputEvents`。
5. 在 `HOME_UI_PREFABS` 注册 `rootName/layer/path`。
6. 在 `HOME_UI_STARTUP_ROOT_NAMES` 或 `HOME_UI_ENTRY_ROOT_NAMES` 中选择启动/按需加载。
7. 默认优先按需加载；只有登录后立即必用且很小的通用弹窗才进入启动组。
8. 在对应 Feature 中处理打开、刷新、关闭，不把业务塞进 `MainHomeView.onLoad()`。
9. 给节点路径、输入阻挡和入口分组增加自动检查。

当前清单的唯一来源是：

```text
assets/Script/UI/Home/HomeUIPrefabManifest.ts
```

不要在多个脚本中维护第二份 Prefab 路径表。

## 7. Home 代码组织

### 7.1 文件职责

| 文件 | 允许职责 |
|---|---|
| `MainHomeView.ts` | 生命周期、入口编排、Prefab 挂载、Scope 所有权 |
| `HomeViewBase.ts` | 跨 Feature 公共契约与少量共享状态 |
| `HomeViewRoleBag.ts` | Role/Bag/Duel 遗留状态显式初始化 |
| `HomeViewAdventure.ts` | Battle/Magic/Beast 遗留状态显式初始化 |
| `HomeFeature*.ts` | 单一玩法或单一页面职责 |
| `HomeConfig.ts` | 资源路径、布局常量、演示配置和候选动画名 |
| `HomeTypes.ts` | DTO、状态、Inspector 和 UI 类型 |
| `HomeUIPrefabManifest.ts` | Prefab 清单与入口分组 |
| `HomeAssetBundleManifest.ts` | 资源路径和入口到 Bundle 的路由 |

### 7.2 新代码放置判断

- 新增一个页面行为：放入该页面的 `HomeFeatureXxx.ts`。
- 新增一种资源路径或布局常量：放入 `HomeConfig.ts` 或独立领域配置。
- 新增 DTO/状态类型：放入 `HomeTypes.ts` 或后端 `GameBackendTypes.ts`。
- 新增跨页面基础设施：先判断是否属于 Service/Manager，不要直接放进 Base。
- 新增生命周期编排：只有确实需要跨 Feature 协调时才进入 MainHomeView。

禁止：

- 重新创建 `HomeViewCommunity` 一类巨型功能文件。
- 为新功能增加 `MainHomeView -> XxxView -> YyyView` 继承层。
- 在点击回调中散落资源路径、接口 URL 和大段演示数据。
- 未声明就覆盖已有 Feature 方法。

### 7.3 Feature 组合规则

`HomeFeatureComposer.ts` 会把 Feature 原型方法组合到现有 Component，不创建额外继承层。

- 无状态 Feature 使用 `composeStatelessFeature`。
- 有状态 Feature 必须提供显式初始化器，并使用 `composeStatefulFeature`。
- Feature 构造函数不会被执行，不能依赖字段初始化器偷偷创建状态。
- 方法重名默认报错；合法覆盖必须在 `overrides` 中显式声明。
- Feature 依赖宿主能力时，应通过 TypeScript 契约声明，不依赖隐式 `any`。

新增 Feature 后同步更新 `check:architecture` 的职责、方法或体积约束，防止文件再次无限增长。

```text

```

### 8.2 判断资源放哪里

放入功能 Bundle：

- 只在一个玩法首次进入后使用。
- 体积较大，启动阶段不需要。
- 可以随该玩法 Scope 释放。

放入 `res`：

- Loading、登录、主城启动必需。
- 被多个功能真实共享。
- 字体、通用按钮、通用品质框、物品基础图等公共基础设施。

放入 `ui-home`：

- 页面与弹窗 Prefab。
- 不应把大纹理或 Spine 因 Prefab 硬引用重新复制进该 Bundle。

不要为了降低某个 Bundle 数字，把真正共享的资源错误塞进另一个功能包。判断标准是生命周期和真实复用关系，不是目录看起来是否整齐。

### 8.3 新资源接入步骤

1. 确定正式文件名、格式和归属目录。
2. 导入资源与 `.meta`，等待 Creator 完成处理。
3. 若是动态资源，在 `HomeConfig.ts` 集中定义路径。
4. 若属于功能包，在 `HomeAssetBundleManifest.ts` 增加前缀或明确路径规则。
5. 把入口加入 `HOME_ENTRY_ASSET_BUNDLES`，确保点击前先获取对应 Bundle。
6. 使用当前页面/玩法的 ResourceScope 加载并 retain。
7. 执行 `npm run check:resources` 和 `npm run check:bundles`。
8. 实跑确认 MainScene 启动时不会提前请求新功能包。

## 9. 资源生命周期与内存

### 9.1 必须通过 ResourceScope

标准模式：

```ts
private readonly resourceScope =
    ResourceManager.instance.createScope('FeatureName');

const bundle = await this.resourceScope.acquireBundle('feature-name');
const asset = this.resourceScope.retain(loadedAsset);

protected onDestroy(): void {
    this.resourceScope.dispose();
}
```

规则：

- 不在业务脚本中直接长期保存 `assetManager.loadBundle` 结果。
- 同一 Scope 对同一 Bundle/Asset 只持有一次。
- View 销毁前先停止使用资源，再 dispose Scope。
- 对象池中的节点未真正销毁时，其 Scope 不能提前释放。
- 异步加载完成后先检查宿主和父节点是否仍有效。
- 页面关闭即释放还是保留到 Home 销毁，应按复用频率和内存评估决定。

### 9.2 必须清理的运行时对象

页面关闭或组件销毁时检查：

- `screen/node/input` 等事件监听。
- `schedule/unschedule`。
- Tween 和延迟回调。
- Spine 完成监听与 TrackEntry 回调。
- 音频播放与 AudioClip 引用。
- 动态创建节点和对象池借出对象。
- 网络请求取消、过期响应和重复提交状态。
- ResourceScope。

长时间在魔界、战斗、兽卡、档案间切换后，Bundle 引用数和保留 Asset 数不应持续只增不减。

## 10. 后端接入标准

### 10.1 唯一调用入口

页面只能调用：

```ts
GameBackend.api
```

后端实现：

```text
assets/Script/Services/Backend/
  IGameBackend.ts
  GameBackendTypes.ts
  GameBackend.ts
  LocalPreviewBackend.ts
  RemoteGameBackend.ts
```

`LocalPreviewBackend` 是明确的离线演示模式；`RemoteGameBackend` 是真实 HTTP 传输实现。禁止一个页面同时从 Remote 和 localStorage 读取同一线上字段。

### 10.2 新接口开发顺序

1. 与后端锁定 OpenAPI、请求/响应示例、错误码和幂等规则。
2. 在 `GameBackendTypes.ts` 定义 DTO，不直接把后端原始对象散进 UI。
3. 在 `IGameBackend` 增加能力。
4. 同时实现 `LocalPreviewBackend` 和 `RemoteGameBackend`。
5. 在 Session/Store 层完成 DTO 到前端状态的原子映射。
6. 页面只订阅/读取映射后的状态并发送事务意图。
7. 增加 Loading、Empty、Error、Retry、超时和取消状态。
8. 接线完成后删除该字段对应的 localStorage 线上真值。
9. 测试重复点击、重复响应、断线重试和过期响应。

### 10.3 服务端必须结算

- 验证码、token、刷新和退出。
- 货币、背包、装备和角色成长。
- 邮件奖励领取。
- 商城购买、限购与扣款。
- 集市上架、购买、撤单和并发冲突。
- 战斗种子、敌人快照、超时、掉落与胜负。
- 排行和对决结果。

客户端可以做表现预测，但不能把本地计算结果当作最终线上真值。

### 10.4 推荐联调顺序

1. 登录、会话恢复、Bootstrap。
2. 角色、货币、背包只读展示。
3. 邮件。
4. 商城。
5. 集市。
6. 角色养成、装备、分解和合成。
7. 排行。
8. 征战和魔界战斗。
9. 对决。

每完成一个域，就彻底完成该域的真值迁移，不长期维持半本地、半远端状态。

## 11. 屏幕、Widget 与安全区

统一基准：

```text
设计分辨率：750 × 1624
策略：ResolutionPolicy.FIXED_WIDTH
fitWidth：true
fitHeight：false
方向：portrait
```

相关入口：

- `settings/v2/packages/project.json`
- `LoadingScene/Canvas`
- `MainScene/Canvas`
- `assets/Script/Services/DisplayAdapter.ts`

开发规则：

- 不在单个页面重新调用另一套设计分辨率。
- 不使用 `SHOW_ALL` 产生大面积黑边。
- 不使用 `EXACT_FIT` 拉伸人物和 UI。
- 背景需要覆盖不同长宽比；贴边控件使用 Widget。
- 刘海、圆角、手势条附近的按钮使用 `sys.getSafeAreaRect()` 或安全区容器。
- 固定宽度下，长屏会增加可见逻辑高度；不要假设可见高度永远等于 1624。
- Android 构建面板必须选择竖屏；Web 的方向配置不能替代原生方向。

任何人修改 Canvas、项目分辨率或运行时策略后，必须执行：

```powershell
npm run check:display
```

## 12. 事件、异步与交互安全

### 12.1 输入层

- 全屏阻挡弹窗根节点使用 `cc.BlockInputEvents`。
- 装饰节点不抢占触摸，避免透明 Sprite 覆盖按钮。
- 同级后绘制节点通常也更靠近命中前端，调整顺序时同时验证输入。
- 页面切换过程中使用统一 TransitionLoadingLayer，不让用户重复触发入口。

### 12.2 异步加载

必须处理：

- 同一入口并发点击去重。
- 加载失败后允许重新尝试。
- 页面已关闭/节点已销毁时丢弃结果。
- 较早请求晚于较新请求返回时，不覆盖新状态。
- 网络事务按钮在 pending 时禁用或显示明确状态。

### 12.3 Tween、Spine 和 schedule

- 进入页面时启动，退出页面时停止。
- 不在 inactive 页面继续更新倒计时和战斗循环。
- Spine 动画名先通过资源契约或候选数组验证。
- 循环动画和一次性动画分开管理。
- 销毁节点前清除完成回调，避免回调访问无效对象。

## 13. 文件、命名和 Meta

- 类名、TypeScript 文件、Prefab 根节点：`PascalCase`。
- 变量与方法：`camelCase`。
- 常量：`UPPER_SNAKE_CASE`。
- 重复编辑器节点：可读名称加 `_1/_2`。
- 图片：优先英文小写 `snake_case`。
- 正式资源禁止 `新建`、`临时`、`preview`、`final2` 等名称。
- 已投入使用的中文 Spine 路径不为追求形式统一而强制重命名。

删除资源前必须同时确认：

1. 动态路径没有引用。
2. Scene/Prefab UUID 没有引用。
3. 资源和 `.meta` 成对删除。
4. Bundle 清单和配置已经更新。
5. Creator 重新导入后检查通过。

禁止手工伪造已有资源 UUID。新增脚本/资源需要合法 `.meta`，移动已有资源则优先保留原 UUID。

## 14. Cocos 缓存的正确处理

### 14.1 缓存目录

```text
library/
temp/
profiles/
build/
```

这些目录可能让本机工程显示为几百 MB，但不属于源码交付。Creator 首次打开会重新生成它们，这是正常行为。

### 14.2 强制安全规则

> Creator 运行期间绝对不要删除 `library`、`temp` 或 `profiles`。

如果在 Creator 运行时清理缓存，资源数据库仍会读取已删除的 Effect/JSON，可能出现大量：

```text
[Assets] upgradeProperties: the library json of effect(...)
```

正确清理顺序：

1. 保存 Scene/Prefab。
2. 完全退出 Qv1.3 Creator。
3. 确认 Qv1.3 的 Creator 主进程和子进程已经退出。
4. 只删除 Qv1.3 根目录下的 `library/temp/profiles/build`。
5. 重新打开项目。
6. 等待资源导入完全稳定。
7. 再执行类型检查、预览或构建。

不要在清缓存和重新导入过程中修改 Scene/Prefab，也不要把缓存目录当成项目变大的源码问题。

## 21. 常见问题快速定位

### 页面打不开

检查：

1. `HomeUIPrefabManifest.ts` 是否注册。
2. 入口是否分配了 Prefab。
3. 父层是 PageLayer 还是 PopupLayer。
4. Bundle 是否在挂载 Prefab 前获取。
5. 是否被 TransitionLoadingLayer 或透明节点阻挡。

### 图片或 Spine 丢失

检查：

1. 资源和 `.meta` 是否完整。
2. 动态路径是否与 Bundle 内路径一致。
3. atlas 页名是否与 PNG 一致。
4. Prefab 是否硬引用了未提前加载的功能 Bundle。
5. ResourceScope 是否过早 dispose。

### 页面越切内存越大

检查：

1. ResourceScope 是否释放。
2. 是否有永久 Bundle 引用。
3. Tween、schedule、Spine、音频和事件是否停止。
4. 动态节点是否销毁或归还对象池。
5. 按需 Prefab 是否按设计保留到 Home 销毁。

### Android 四周黑边

检查：

1. 项目和两张 Canvas 是否仍为 `750×1624`。
2. `DisplayAdapter` 是否使用 `FIXED_WIDTH`。
3. Android 是否选择竖屏。
4. 是否安装了旧 APK 或使用了旧热更新缓存。
5. WebView/壳层是否本身没有铺满原生窗口。

### Creator 控制台大量 Effect 缓存错误

如果看到 `upgradeProperties` 或 `library json of effect`：

1. 停止操作并退出 Creator。
2. 确认全部 Qv1.3 Creator 进程退出。
3. 删除 `library/temp`。
4. 重新打开并等待完整导入。

不要在 Creator 运行时再次删除缓存。

## 22. 最终原则

Qv1.3 的价值不只是文件更整齐，而是已经建立了能够持续控制复杂度的边界：

- 场景控制常驻结构。
- Prefab 控制页面结构。
- Feature 控制玩法职责。
- Manifest 控制加载入口。
- Bundle 控制资源归属。
- ResourceScope 控制资源寿命。
- Backend 控制线上数据边界。
- 自动门禁控制工程回退。

后续每次开发都应在这些边界内增加能力。若一个需求必须破坏多个边界才能实现，应先重新设计需求落点，而不是直接把逻辑和资源堆回 MainScene 或 MainHomeView。
