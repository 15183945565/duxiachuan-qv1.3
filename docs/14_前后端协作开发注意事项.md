# Qv1.3 前后端协作开发注意事项

更新日期：2026-07-29  
适用工程：`C:\Users\34158\Desktop\game\Qv1.3`  
前端仓库：`duxiachuan-qv1.3`  
后端仓库：`duxiachuan-server`  
后端技术栈：Java、Spring Boot、Maven、JDBC、WebSocket  

本文档的目标不是简单写几条注意事项，而是作为后续前后端一起开发、联调、上线的共同规则。只要这里的规则不被破坏，项目就会越来越稳；如果一边做一边随意改接口、随意存本地数据、随意复制素材和脚本，后面一定会越来越难维护。

## 1. 当前项目结论

Qv1.3 现在已经有正式项目骨架，但还不是完整后端游戏。

当前已经具备：

- Cocos Creator 3.8.8 前端工程。
- `LoadingScene`、`MainScene`、Home 功能页、Popup 层级。
- 前端本地配置数据，例如背包图鉴、道友、分享任务、魔界、征战、兽卡、市场、角色成长表。
- 后端访问边界：`GameBackend.api`、`IGameBackend`、`RemoteGameBackend`、`LocalPreviewBackend`。
- HTTP 请求基础封装、运行时配置入口、Git LFS 管理大资源。

当前还没有完成：

- 真实手机号登录。
- 服务端 token 签发、刷新、失效处理。
- Bootstrap 数据真正回填到 UI。
- 背包、货币、邮件、商城、市场、战斗、角色成长等页面的完整服务端接线。
- Java 后端数据库表、接口、WebSocket 推送、后台运维工具。

一句话：现在前端是可以继续正规开发的半成品客户端，后端要从“账号和主链路”开始接，不要试图第一天把所有系统都接完。

## 2. 仓库分工

建议保持两个仓库：

| 仓库 | 谁主要维护 | 内容 | 不应该放什么 |
|---|---|---|---|
| `duxiachuan-qv1.3` | 前端 | Cocos 项目、前端脚本、UI、资源、构建模板、前端文档 | 后端 Java 代码、数据库密码、服务器私钥 |
| `duxiachuan-server` | 后端 | Spring Boot、Maven、JDBC、WebSocket、数据库脚本、接口文档 | Cocos 的 `assets/library/temp/build` 临时目录 |

前端和后端可以互相看仓库，也可以互相提 issue 和 PR，但不要把两个工程混成一个目录。游戏上线后前端是一个客户端产物，后端是服务器服务，它们生命周期不同，发布方式也不同。

## 3. 开发总原则

### 3.1 一个字段只有一个真值来源

这是最重要的原则。

错误做法：

- 前端 localStorage 存一份元宝，后端数据库也存一份元宝。
- 前端自己扣道具，后端也自己扣道具。
- 邮件领取前端先改状态，后端失败后状态不同步。
- 战斗奖励前端先发，后端结算又发一次。

正确做法：

- 登录态、角色、货币、背包、装备、邮件、商城购买、市场交易、战斗结算，最终都以服务端为准。
- 前端可以短时间展示“乐观 UI”，但服务端返回失败时必须回滚。
- 纯设备设置可以继续留在本地，例如音乐音量、音效音量、静音、画质偏好。

### 3.2 页面不能直接请求后端

前端页面代码不要到处写 `fetch`。

正确路径：

```text
Cocos 页面
-> GameBackend.api
-> IGameBackend
-> RemoteGameBackend
-> 后端 HTTP API
```

好处：

- 以后换接口地址不用到处找。
- 本地预览和真实服务器可以切换。
- 错误处理、超时、token 都能统一。
- 后续自动检查可以防止页面绕过接口层。

### 3.3 接口先定契约再写死逻辑

前后端联调前必须先定接口契约。至少包括：

- 请求路径。
- 请求方法。
- 请求参数。
- 响应字段。
- 错误码。
- 是否需要 token。
- 是否需要幂等键。
- 失败时前端怎么提示。
- 成功后返回完整快照还是局部更新。

不要出现“你先这样写，我后面再改”的长期状态。临时可以，但必须当天写入文档或 issue。

### 3.4 服务端负责安全和最终结算

前端可以负责表现和交互，不能负责最终资产安全。

后端必须负责：

- 登录和 token。
- 元宝、魂力、积分等货币。
- 背包数量。
- 装备和强化状态。
- 邮件奖励领取。
- 商城购买扣款和发货。
- 市场上架、购买、撤单、并发防超卖。
- 战斗开始、战斗过期、战斗结算、奖励发放。
- 排行榜统计。
- 分享任务领取状态。

前端只负责：

- 展示服务端返回的数据。
- 收集玩家操作。
- 调用接口。
- 展示 loading、成功、失败、重试。
- 播放动画和音效。

## 6. API 设计规则

### 6.1 统一响应格式

建议所有接口都返回：

```json
{
  "ok": true,
  "data": {},
  "errorCode": "",
  "message": ""
}
```

成功：

```json
{
  "ok": true,
  "data": {
    "serverTime": 1785331200000
  }
}
```

失败：

```json
{
  "ok": false,
  "errorCode": "NOT_ENOUGH_YUANBAO",
  "message": "元宝不足"
}
```

前端逻辑只判断 `errorCode`，展示文字使用 `message`。

### 6.2 HTTP 状态码建议

| 状态码 | 用途 |
|---|---|
| `200` | 正常成功 |
| `400` | 参数错误 |
| `401` | 未登录或 token 无效 |
| `403` | 已登录但无权限 |
| `404` | 资源不存在 |
| `409` | 状态冲突，例如重复领取、库存变化 |
| `429` | 请求过快 |
| `500` | 服务端异常 |

业务失败不要全部用 500。比如元宝不足、材料不足、邮件已领取，这些都是业务错误，不是服务器崩了。

### 6.3 错误码必须稳定

建议第一批错误码：

| 错误码 | 含义 |
|---|---|
| `UNAUTHORIZED` | 未登录 |
| `TOKEN_EXPIRED` | token 过期 |
| `INVALID_ARGUMENT` | 参数不合法 |
| `PLAYER_NOT_FOUND` | 玩家不存在 |
| `ROLE_NOT_CREATED` | 尚未创建角色 |
| `NOT_ENOUGH_YUANBAO` | 元宝不足 |
| `NOT_ENOUGH_ITEM` | 道具不足 |
| `MAIL_NOT_FOUND` | 邮件不存在 |
| `MAIL_ALREADY_CLAIMED` | 邮件已领取 |
| `PRODUCT_NOT_FOUND` | 商品不存在 |
| `PRODUCT_OFFLINE` | 商品已下架 |
| `MARKET_LISTING_CHANGED` | 市场挂单已变化 |
| `BATTLE_NOT_FOUND` | 战斗不存在 |
| `BATTLE_EXPIRED` | 战斗已过期 |
| `DUPLICATE_REQUEST` | 重复请求 |
| `SERVER_MAINTENANCE` | 维护中 |
| `FORCE_UPDATE_REQUIRED` | 需要强制更新 |

### 6.4 所有资产事务都要幂等

以下接口必须带 `requestId` 或 `idempotencyKey`：

- 邮件领取。
- 一键领取。
- 商城购买。
- 市场购买。
- 市场上架。
- 市场撤单。
- 背包使用。
- 背包分解。
- 装备强化。
- 角色突破。
- 战斗结算。
- 分享任务领取。

示例：

```json
{
  "requestId": "client_15183945565_20260729_000001",
  "mailId": "mail_1001"
}
```

同一个玩家、同一个 `requestId` 重复请求，后端要返回第一次处理结果，不能重复扣款或重复发奖。

### 6.5 时间统一用服务端时间

需要服务端时间的地方：

- 登录态过期。
- 邮件创建时间和过期时间。
- 魔界倒计时。
- 战斗过期时间。
- 对决回合倒计时。
- 活动开始和结束。
- 限购刷新。

前端可以显示倒计时，但基准必须来自 `serverTime`。

## 7. Bootstrap 设计建议

`GET /v1/game/bootstrap` 是前端进入主界面最重要的接口。

建议返回：

```json
{
  "ok": true,
  "data": {
    "serverTime": 1785331200000,
    "account": {
      "id": "account_1",
      "phone": "15183945565"
    },
    "profile": {
      "id": "role_1",
      "uid": "9740495290",
      "name": "秘境少侠",
      "gender": "male",
      "level": 1,
      "battleLevel": 1,
      "power": 125
    },
    "currencies": {
      "yuanbao": 0,
      "soul": 0,
      "points": 0
    },
    "inventory": [],
    "equipments": [],
    "redDots": {
      "mail": false,
      "share": false
    },
    "featureFlags": {
      "market": true,
      "duel": true,
      "magic": true
    }
  }
}
```

注意：

- Bootstrap 不一定要把所有大列表都返回，但主界面第一屏需要的数据必须返回。
- 返回字段要稳定，不要今天叫 `gold`，明天叫 `yuanbao`。
- 如果某些功能没开放，用 `featureFlags` 控制，前端隐藏或置灰入口。
- Bootstrap 应该在登录成功和关键事务成功后都能刷新，保证前端状态恢复。

## 8. WebSocket 使用边界

后端同学用 WebSocket 是合理的，但不要所有东西都用 WebSocket。

适合 HTTP 的：

- 登录。
- Bootstrap。
- 邮件列表。
- 商城购买。
- 背包查询。
- 角色强化。
- 战斗开始和结算。

适合 WebSocket 的：

- 实时排行榜刷新。
- 对决匹配。
- 房间状态。
- 战斗房间多人同步。
- 服务器公告推送。
- 被动红点推送。

建议 WebSocket 消息格式：

```json
{
  "type": "MAIL_RED_DOT_CHANGED",
  "requestId": "",
  "serverTime": 1785331200000,
  "data": {
    "hasUnread": true
  }
}
```

WebSocket 注意事项：

- 连接成功后要鉴权。
- 断线要重连。
- 重连后要重新拉 Bootstrap 或关键状态。
- 推送只做提醒，最终数据仍通过 HTTP 拉取或通过服务端权威消息更新。
- 不要用 WebSocket 传生产密钥。

## 9. 前端开发注意事项

### 9.1 Cocos 编辑器节点

当前项目很多 UI 是“编辑器节点 + 脚本补全”的混合方式。后续开发要注意：

- 能在编辑器里摆的固定 UI，优先在编辑器里摆。
- 脚本负责绑定、刷新、动态列表、状态切换。
- 不要让脚本每次运行都强行覆盖你在编辑器里调好的位置和大小。
- 如果一个节点后续要经常调位置，脚本应该读取现有节点，不要每次重建。
- 动态列表的行节点应该有独立模板或独立容器，不要把多个信息框散落在外层。

### 9.2 页面层级

建议继续保持：

```text
MainScene
└─ Canvas
   └─ MainRoot
      ├─ GameSceneLayer
      ├─ HudLayer
      ├─ PageLayer
      ├─ PopupLayer
      ├─ GuideLayer
      └─ ToastLayer
```

含义：

| 层 | 作用 |
|---|---|
| `GameSceneLayer` | 主城、地图、角色等场景表现 |
| `HudLayer` | 常驻按钮、货币、入口 |
| `PageLayer` | 全屏功能页 |
| `PopupLayer` | 弹窗 |
| `GuideLayer` | 新手引导 |
| `ToastLayer` | 短提示 |

不要把弹窗放到 Page 里，也不要把常驻 HUD 放到某个功能页里。

### 9.3 数据刷新

页面打开时：

```text
显示 loading
-> 读当前 Store 快照
-> 如有必要请求后端
-> 成功后刷新 UI
-> 失败显示重试或 toast
```

事务操作时：

```text
禁用按钮
-> 调接口
-> 成功更新 Store 和 UI
-> 失败恢复按钮并提示
```

不要出现：

- 按钮可重复点导致多次购买。
- 前端先扣数量，失败后不恢复。
- 页面关闭了，请求回来还继续改已销毁节点。
- 一个页面直接改另一个页面的内部节点。

### 9.4 本地预览与真实后端

`LocalPreviewBackend` 只用于：

- 无服务器演示。
- UI 验收。
- 前端离线开发。

`RemoteGameBackend` 用于：

- Mock Server。
- 测试服。
- 预发布。
- 生产服。

不要在真实联调模式下静默回退到本地预览。否则会出现“看起来能玩，其实没走后端”的假成功。

### 9.5 资源规范

前端资源注意：

- 图片、Spine、音频、字体继续走 Git LFS。
- 不要提交 `library/`、`temp/`、`build/` 这类生成目录。
- 资源命名要稳定，改名会影响 prefab 和脚本引用。
- 大资源上线前要评估首包大小。
- `runtime-config.js` 不要写死生产密钥。

### 9.6 字体和中文

当前项目有些终端输出出现中文乱码迹象。后续要注意：

- 源码统一 UTF-8。
- 文档统一 UTF-8。
- 后端返回 JSON 使用 UTF-8。
- 数据库连接设置 UTF-8。
- 不要把乱码中文写入数据库配置表。

如果以后要裁剪字体，必须先确认：

- 固定 UI 文案字库。
- 后端公告字库。
- 用户昵称允许字符。
- 缺字回退方案。

## 10. 后端开发注意事项

### 10.1 Spring Boot 分层建议

建议后端结构：

```text
com.duxiachuan.server
├─ controller
├─ service
├─ repository
├─ domain
├─ dto
├─ config
├─ security
├─ websocket
└─ common
```

职责：

| 层 | 作用 |
|---|---|
| `controller` | 接口入口，只做参数接收和响应 |
| `service` | 业务事务，扣款、发奖、校验 |
| `repository` | JDBC 数据访问 |
| `domain` | 领域对象和枚举 |
| `dto` | 前后端传输对象 |
| `security` | token、鉴权、登录上下文 |
| `websocket` | 长连接推送 |
| `common` | 通用响应、错误码、异常处理 |

### 10.2 JDBC 注意事项

用 JDBC 没问题，但要注意：

- 所有 SQL 参数必须用占位符，不能字符串拼接玩家输入。
- 资产变更必须使用事务。
- 市场购买、邮件领取、战斗结算必须防重复。
- 重要资产表更新要考虑行锁或乐观锁。
- 金额和价格不要用浮点数存，建议用整数最小单位或 `BigDecimal`。
- 每个事务成功后写资产流水。

### 10.3 Maven 注意事项

建议固定：

- Java 版本。
- Spring Boot 版本。
- 数据库驱动版本。
- 测试依赖。
- 打包插件。

不要每个人本地版本不一样。仓库里要有 `pom.xml`，并能通过：

```powershell
mvn test
mvn package
```

### 10.4 安全注意事项

后端不能信任前端传来的：

- 玩家 ID。
- 元宝数量。
- 背包数量。
- 战力。
- 战斗奖励。
- 是否胜利。
- 市场价格合法性。
- 任务是否完成。

前端传玩家操作，后端根据数据库和规则计算结果。

### 10.5 日志和排查

每个请求建议有：

- `requestId`。
- `accountId`。
- `playerId`。
- 接口路径。
- 错误码。
- 耗时。

资产变更必须能追踪：

```text
谁
在什么时间
因为什么接口
扣了什么
发了什么
请求 ID 是什么
```

没有资产日志，后面玩家反馈“我元宝没到账”会很难查。

## 11. 前后端联调顺序

不要从最复杂的魔界、市场、对决开始。建议按下面顺序。

### 11.1 第一阶段：登录和 Bootstrap

目标：

```text
打开游戏 -> 手机号登录 -> 拿 token -> 进入 MainScene -> 拉 Bootstrap -> 显示角色名和货币
```

验收：

- 正确手机号能登录。
- token 失效会回登录。
- 刷新游戏后能恢复登录态。
- 主界面显示服务端角色名。
- 前端不再靠写死 UID 当真实数据。

### 11.2 第二阶段：背包和邮件

目标：

```text
服务端发一封邮件 -> 前端看到邮件 -> 领取奖励 -> 背包增加 -> 邮件状态变已领取
```

验收：

- 重复点击领取不会重复发奖。
- 一键领取不会重复发奖。
- 断网失败可以重试。
- 领取后不用重启，背包立即刷新。

### 11.3 第三阶段：商城

目标：

```text
商城列表 -> 购买挑战卡/保护卡/战力卡 -> 扣元宝 -> 发道具 -> 玩法里能使用
```

验收：

- 余额不足提示准确。
- 商品下架提示准确。
- 重复点击不会重复扣款。
- 道具数量刷新准确。

### 11.4 第四阶段：征战主链路

目标：

```text
进入征战 -> 开始战斗 -> 提交结算 -> 服务端发奖励 -> 背包刷新
```

验收：

- 每场战斗都有 `battleId`。
- 过期战斗不能结算。
- 重复提交不能重复发奖。
- 奖励数量由服务端决定。

### 11.5 第五阶段：角色成长

目标：

```text
使用经验材料 -> 升级 -> 突破 -> 装备强化 -> 战力刷新
```

验收：

- 材料不足由服务端拒绝。
- 战力变化和属性变化一致。
- 强化失败或超时不会扣错材料。

### 11.6 第六阶段：分享和道友

目标：

```text
读取道友列表 -> 计算任务进度 -> 完成后领取元宝 -> 元宝刷新
```

验收：

- 首席道友和一代道友数据来自服务端。
- 任务完成状态来自服务端。
- 领取元宝幂等。
- 前往按钮能打开道友页。

### 11.7 第七阶段：市场、魔界、对决、兽卡

这些系统复杂度更高，建议后接。

优先顺序：

1. 市场。
2. 魔界。
3. 对决。
4. 兽卡收益。

## 12. Git 协作规则

### 12.1 分支建议

建议：

| 分支 | 作用 |
|---|---|
| `main` | 稳定可运行版本 |
| `dev` | 日常集成开发 |
| `feature/xxx` | 具体功能开发 |
| `fix/xxx` | 修复问题 |

不要所有人直接往 `main` 乱推。

### 12.2 提交前必须做

前端提交前：

```powershell
npm run check:all
```

后端提交前：

```powershell
mvn test
```

如果暂时没有测试，也要至少启动项目确认不报错。

### 12.3 Commit 信息

建议格式：

```text
feat: add phone login api
fix: repair mail claim idempotency
docs: add frontend backend collaboration notes
chore: update git lfs patterns
```

不要写：

```text
修改
111
随便改一下
```

### 12.4 不要提交的内容

前端不要提交：

- `library/`
- `temp/`
- `build/`
- `local/`
- 日志文件。
- 截图临时文件。
- 个人 IDE 缓存。

后端不要提交：

- 数据库真实密码。
- 服务器私钥。
- `.env` 生产配置。
- target 编译产物。
- 本地日志。

## 13. 接口文档维护规则

每新增一个接口，必须写清楚：

```text
接口名：
路径：
方法：
是否需要 token：
请求 JSON：
成功响应 JSON：
失败错误码：
幂等规则：
前端调用页面：
验收方式：
```

接口改字段时：

- 先改文档。
- 再改后端。
- 再改前端 DTO。
- 最后联调。

不要口头说完就算了。口头约定没有版本记录，后面必然互相忘。

## 14. 上线前必须检查

### 14.1 前端检查

- Cocos 构建无报错。
- `npm run check:all` 通过。
- 登录、主界面、背包、邮件、商城、征战主链路可走通。
- 所有按钮有 loading、防重复点击、失败提示。
- 断网、超时、401、500 都能恢复。
- 资源没有丢失。
- 手机尺寸无明显错位。
- 首包大小和资源加载可接受。

### 14.2 后端检查

- `mvn test` 通过。
- 数据库迁移脚本可重复执行或有版本管理。
- 所有资产接口有事务。
- 所有资产接口有幂等。
- token 过期和刷新正常。
- 日志能查到请求和资产流水。
- WebSocket 断线重连正常。
- 压测核心接口。
- 数据库备份方案明确。

### 14.3 共同检查

- 前后端使用同一份接口文档。
- 测试服、预发布、生产服地址明确。
- CORS 配置正确。
- HTTPS/WSS 正常。
- 强制更新和维护公告可用。
- 出问题能回滚前端资源或后端版本。

## 15. 红线

这些事情尽量不要做，一旦做了后面会很痛苦：

1. 不要让前端直接相信自己本地的元宝和背包。
2. 不要让一个字段同时存在 localStorage 和数据库两个真值。
3. 不要绕过 `GameBackend.api` 直接请求后端。
4. 不要把接口字段随口改名。
5. 不要把生产密钥提交到 GitHub。
6. 不要把 Cocos 的 `library`、`temp`、`build` 当源码提交。
7. 不要在没有幂等的情况下做领取、购买、结算。
8. 不要用浮点数直接做真实货币和价格结算。
9. 不要把所有玩法第一轮一起接后端。
10. 不要在联调失败时偷偷改成本地数据假装成功。

## 17. 最终判断标准

后续开发不是看“页面能不能点”，而是看下面这些是否成立：

- 玩家数据服务端可恢复。
- 资产变化有事务。
- 重复请求不会重复发奖。
- 前端刷新后状态不丢。
- 后端挂了前端有明确失败提示。
- 接口字段有文档。
- Git 记录能追踪谁改了什么。
- 新同学接手能看懂结构。
- 上线后出问题能定位、能回滚、能补偿。

如果这些都能做到，这个项目就不是一个临时拼出来的 demo，而是可以继续往多人在线、长期运营方向走的正式项目。
